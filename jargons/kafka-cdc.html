초보자를 위한 왜 CDC가 필요한가? (이중 작성 문제 해결)부터 Debezium 트랜잭션 로그 실시간 스트리밍까지

🌱 1. [초보자 필독] CDC가 왜 필요한가요? (이중 작성의 악몽)

❌ 전통적인 방식: 앱에서 직접 2군데 쓰기 (Dual Write 문제)

회원이 닉네임을 변경할 때, 백엔드 스프링 앱에서 다음과 같이 코드를 짰다고 가정해 봅시다.
1) MySQL DB에 UPDATE 쿼리 날림 (성공!)
2) Elasticsearch 검색엔진에 변경 반영 API 호출 (네트워크 장애로 실패! 💥)
👉 결과: DB에는 새 닉네임이 있는데, 검색엔진에서는 옛날 닉네임으로 검색되는 치명적 데이터 불일치 발생!

✅ CDC (Change Data Capture) 방식: DB의 'CCTV 일기장'을 감시하기

앱은 오직 MySQL DB에만 평소처럼 저장하고 끝냅니다. 대신 CDC 엔진(Debezium)이 MySQL이 내부적으로 기록하는 트랜잭션 로그(Binlog / WAL)라는 일기장을 실시간으로 훔쳐보고 있다가, 변경 사항이 감지되는 즉시 Kafka 이벤트로 발행하여 Elasticsearch, Redis, 데이터웨어하우스로 안전하게 배달해 줍니다.

📝 3. Debezium이 캡처한 변경 이벤트 JSON 페이로드 실제 모습

DB에서 UPDATE가 발생했을 때 Debezium이 생성하여 Kafka로 전송하는 메시지에는 변경 이전 값(before)과 이후 값(after)이 완벽히 포함됩니다. 

{
  "schema": { ... },
  "payload": {
    "before": {
      "id": 101,
      "username": "hong_old",
      "email": "hong@test.com"
    },
    "after": {
      "id": 101,
      "username": "hong_new_king", // 닉네임 수정 감지!
      "email": "hong@test.com"
    },
    "op": "u", // 'c'=Create, 'u'=Update, 'd'=Delete
    "ts_ms": 1723351200000
  }
}

💡 4. 백엔드 아키텍처 관점의 3대 결정적 이점

1. Zero Code Mutation (코드 무수정)

백엔드 Spring Boot 소스코드를 단 한 줄도 고칠 필요가 없습니다. DB 엔진 레벨에서 동작하므로 비즈니스 로직과 데이터 동기화 책임이 완벽히 분리됩니다.

2. Near Real-time (0.1초 내 전파)

배치(Batch) 프로그램처럼 1시간마다 DB를 무겁게 SELECT 풀스캔할 필요 없이, 로그가 쓰이는 순간 밀리초(ms) 단위로 Kafka에 실시간 스트리밍됩니다.
