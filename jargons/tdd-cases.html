선착순 재고 차감 비즈니스 로직을 통해 살펴보는 Red ➔ Green ➔ Refactor 3단계 코드 점진적 발전 과정

🔄 1. TDD 3단계 순환 개발 사이클 (Red-Green-Refactor)

1. RED
실패하는 단위 테스트 먼저 작성
➔
2. GREEN
테스트 통과 최소한의 코드 구현
➔
3. REFACTOR
도메인 캡슐화 & 클린 코드 리팩토링

💻 2. TDD 사이클에 맞춘 실제 코드 진화 과정

1단계 : RED (실패하는 테스트 코드 작성)

아직 OrderService나 decreaseStock 메서드가 없거나 구현되지 않은 상태에서 요구사항을 검증하는 JUnit 5 단위 테스트를 먼저 작성합니다. (실행 시 빨간 불 ❌) 

// [JUnit 5 & AssertJ 단위 테스트]
@Test
@DisplayName("재고가 부족할 때 주문을 시도하면 StockEmptyException 예외가 발생한다")
void shouldThrowExceptionWhenStockIsInsufficient() {
    // Given (준비: 재고가 1개인 상품)
    Product product = new Product("PROD-101", 1);
    
    // When & Then (실행 및 검증: 2개 주문 시도 시 예외 발생 검증)
    assertThatThrownBy(() -> orderService.placeOrder(product, 2))
        .isInstanceOf(StockEmptyException.class)
        .hasMessage("재고가 부족합니다.");
}

2단계 : GREEN (테스트 통과를 위한 최소 코드 구현)

예쁜 구조를 고민하지 않고 오직 위 테스트를 빠르게 통과(초록 불 ✅)시키는 가장 단순한 코드를 작성합니다. 

// [OrderService.java - 최소 구현]
public void placeOrder(Product product, int quantity) {
    if (product.getStock() < quantity) {
        throw new StockEmptyException("재고가 부족합니다.");
    }
    product.setStock(product.getStock() - quantity); // 일단 통과용 세터 사용
}

3단계 : REFACTOR (도메인 캡슐화 및 객체지향 리팩토링)

테스트가 든든하게 받쳐주고 있으므로, 안심하고 서비스의 로직을 Product 도메인 엔티티 내부로 캡슐화하고 Setter를 제거합니다. 테스트는 여전히 초록 불 ✅ 유지! 

// [Product.java - 도메인 모델 패턴 리팩토링]
public class Product {
    private String id;
    private int stock;

    // 비즈니스 로직을 엔티티 스스로 검증하고 처리하도록 캡슐화
    public void decreaseStock(int quantity) {
        if (this.stock < quantity) {
            throw new StockEmptyException("재고가 부족합니다.");
        }
        this.stock -= quantity;
    }
}

// [OrderService.java - 깔끔해진 서비스 레이어]
public void placeOrder(Product product, int quantity) {
    product.decreaseStock(quantity);
}
