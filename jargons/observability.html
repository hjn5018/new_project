🔭 ELK vs OpenTelemetry vs LGTM (Grafana) 관제 비교

로그 중심(ELK), 표준 분산 트레이싱(OTel), 오픈소스 메트릭/로그/트레이스 올인원 스택(LGTM)의 실무 시나리오별 예시

📊 1. 관제 솔루션 3대 패러다임 비교표

구분 ELK Stack OpenTelemetry (OTel) LGTM (Grafana Stack)
핵심 정체성 대용량 전문 검색 기반 로그(Log) 분석 벤더 독립적 수집 표준 SDK & 에이전트 Grafana 대시보드 중심 풀스택 관제 (Loki, Tempo, Mimir)
분산 트레이싱 별도 APM 라이브러리 연동 필요 글로벌 표준 (W3C Trace Context) Tempo를 통한 초고속 트레이스 조회
비용 & 리소스 전문 인덱싱으로 디스크/메모리 비용 큼 수집 전용이므로 저장소 비용은 백엔드에 종속 Loki 레이블 인덱싱으로 비용 80% 절감

🚨 2. 실무 장애 해결 시나리오 (쇼핑몰 결제 지연 50ms ➔ 4,000ms 폭증 시)

1. ELK 스택의 접근법

Kibana에서 log.level: "ERROR" OR response_time > 3000 검색어로 쿼리를 날려, 특정 시간에 발생한 에러 로그 텍스트와 스택 트레이스를 집중 검색합니다.

2. OpenTelemetry의 접근법

하나의 요청에 부여된 TraceId를 따라 [게이트웨이 ➔ 주문 ➔ 결제 ➔ PG사 호출] 전체 구간의 Span 시각 타임라인을 확인하여 "PG사 외부 API 호출 구간에서 3.8초가 걸렸다"는 병목 지점을 1초 만에 찾아냅니다.

3. LGTM (Grafana)의 접근법

Grafana 화면 하나에서 Mimir(메트릭 경고 그래프) ➔ 클릭 한 번으로 Tempo(해당 시점 트레이스) ➔ Loki(연관 로그)가 완벽히 이어지는 원클릭 드릴다운을 수행합니다.
