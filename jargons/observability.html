🔭 ELK vs OpenTelemetry vs LGTM (Grafana) 관제 심층 비교

역색인 비용, 벤더 독립성(Vendor-Agnostic), Loki 레이블 인덱싱 비용 절감 원리 완벽 해설

📊 1. 관제 솔루션 3대 패러다임 비교표

구분 ELK Stack OpenTelemetry (OTel) LGTM (Grafana Stack)
핵심 정체성 대용량 전문 검색 기반 로그(Log) 분석 벤더 독립적 수집 표준 SDK & 에이전트 Grafana 대시보드 중심 풀스택 관제 (Loki, Tempo, Mimir)
분산 트레이싱 별도 APM 라이브러리 연동 필요 글로벌 표준 (W3C Trace Context) Tempo를 통한 초고속 트레이스 조회
비용 & 리소스 전문 역색인으로 디스크/메모리 비용 큼 수집 전용이므로 저장소 비용은 백엔드에 종속 Loki 레이블 인덱싱으로 비용 80% 절감

💡 2. [심층 해설] 관제 아키텍처 3대 핵심 질문 답변

❓ 1. ELK의 '전문 인덱싱(Inverted Index)'과 높은 리소스 비용, 그리고 APM 라이브러리란?

• 전문 역색인(Inverted Index)이란?: 책 맨 뒤의 '색인(Index)'처럼, 로그 본문의 모든 단어(단어 하나하나)를 쪼개어 거대한 B-Tree 색인 사전을 만듭니다. 검색 속도는 0.01초로 극도로 빠르지만, 원본 로그 크기보다 색인 파일 크기가 더 커질 정도로 메모리(RAM)와 디스크(SSD)를 엄청나게 잡아먹습니다.
• 별도 APM 라이브러리: Elastic APM Java Agent, Pinpoint, Scouter, SkyWalking 같은 에이전트를 JVM에 붙여야 메서드 실행시간 및 트랜잭션 호출 트리를 추적할 수 있습니다.

❓ 2. OpenTelemetry(OTel)가 '벤더 독립적(Vendor-Agnostic)'이라는 뜻은?

과거에는 Datadog을 쓰려면 Datadog 전용 SDK를 코드에 심고, New Relic으로 바꾸려면 전사 소스코드를 전부 뜯어고쳐야 했습니다(벤더 종속).
반면 OpenTelemetry(CNCF 오픈소스 표준)는 전 세계 클라우드 기업들이 합의한 단일 표준 SDK입니다. 백엔드 코드에는 OTel만 한 번 심어두면, 설정 파일의 주소 한 줄만 바꿔서 오늘은 Grafana Tempo, 내일은 Datadog, 모레는 AWS CloudWatch로 데이터를 마음대로 쏠 수 있습니다.

❓ 3. Grafana Loki의 '레이블 인덱싱'은 어떻게 비용을 80% 절감하나요?

• Elasticsearch는 로그 내용 안의 모든 글자를 무겁게 인덱싱합니다.
• 반면 Loki는 오직 메타데이터 레이블(app=order-service, env=prod)만 가볍게 인덱싱하고, 로그 본문은 그대로 압축하여 매우 저렴한 오브젝트 스토리지(AWS S3 / GCP GCS)에 통째로 보관합니다.
👉 따라서 색인 구축에 필요한 고성능 RAM과 SSD 비용을 80% 이상 절감할 수 있습니다!
