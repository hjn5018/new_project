📡 EDA (이벤트 기반 아키텍처) & MQTT vs RabbitMQ vs Kafka

비동기 결합 해제(Decoupling)의 원리와 대용량 엔터프라이즈 메시징 vs 초경량 IoT 프로토콜 및 MQTT QoS 레벨 완벽 분석

💡 1. EDA의 비동기 결합 해제(Decoupling)와 엔터프라이즈 환경

전통적인 MSA에서는 주문 서비스가 결제, 배송, 알림 서비스의 IP와 API 주소를 모두 알고 직접 호출해야 했습니다. 하지만 EDA(Event-Driven Architecture)에서는 서비스 간의 직접 의존 관계를 완전히 끊어냅니다(결합 해제 / Decoupling).

🚀 비동기 결합 해제 (Decoupling)의 실무 가치

  • 발행자-구독자 독립성: 주문 서비스는 알림 서비스가 배포 중이거나 다운되어도 전혀 영향받지 않고 오직 브로커에 이벤트만 발행 후 정상 종료.
  • 신규 비즈니스 확장성: 추후 '추천 AI 분석 서비스'나 '마케팅 쿠폰 서비스'가 새로 추가되어도 주문 서비스 코드는 단 한 글자도 수정할 필요 없이 새 서비스가 이벤트만 구독하면 됨.

🌐 대용량 데이터 보관 & 브로드밴드 네트워크

  • 고속 브로드밴드(10Gbps+) 전제: AWS, GCP 등의 데이터센터 내부 백본망은 대역폭이 매우 넓고 안정적이므로 대용량 JSON/Protobuf/Avro 메시지를 초당 수십만 건씩 처리.
  • 데이터 영속성(Persistence): Kafka 등은 메시지를 디스크 로그에 수일~수개월간 보관하므로 장애 복구 후 재처리(Replay) 가능.

🆚 2. MQTT vs RabbitMQ vs Kafka 핵심 차이점 분석

MQTT와 RabbitMQ는 모두 '메시지 브로커' 역할을 할 수 있지만, 탄생 목적과 네트워크 환경이 완전히 다릅니다.

비교 항목 MQTT RabbitMQ Apache Kafka
탄생 목적 & 환경 초경량 IoT 기기 통신
(불안정한 3G/LTE, 배터리/대역폭 제한)		 엔터프라이즈 비즈니스 메시지 큐
(신뢰성 있는 트랜잭션 라우팅)		 대용량 분산 실시간 이벤트 스트리밍
(초당 수백만 건 빅데이터 로그)
패킷 헤더 크기 최소 2 Byte (극도의 경량화) 수십~수백 Byte (AMQP 규격) 수십~수백 Byte (Kafka 프로토콜)
메시지 라우팅 방식 계층형 토픽 (예: factory/sensor1/temp) 다양한 Exchange (Direct, Fanout, Topic, Headers) 파티션 기반 고속 스트리밍 (Key Hash 기반)
메시지 보관 (영속성) 소비 즉시 소멸 (브로커 메모리 중심) Consumer Ack 즉시 큐에서 삭제 디스크 분산 로그 영구 보관 (Replay 가능)
대표 사용처 스마트워치 심박수 전송, 스마트홈 센서 E-Commerce 주문 결제 대기열, 이메일 발송 큐 사용자 행동 로그 수집, 실시간 결제 스트림

📶 3. MQTT QoS (Quality of Service) 3단계 레벨 상세 분석

네트워크가 불안정한 IoT 환경에서 메시지가 누락되거나 중복 전송되는 것을 제어하기 위해 MQTT는 3단계 전송 품질(QoS)을 제공합니다.

QoS 0 : At most once

최대 1회 전송 (Fire and Forget)

메시지를 딱 1번 전송하고 응답을 확인하지 않습니다. 네트워크가 끊기면 유실될 수 있습니다.

Client ➔ [PUBLISH] ➔ Broker
(수신 확인 없음, 최고 속도)

💡 사용처: 1초마다 갱신되는 온습도 센서, 실시간 GPS 좌표 (한 번 유실되어도 다음 데이터가 곧 오므로 무방한 경우)

QoS 1 : At least once

최소 1회 전송 (확인 응답 수신)

브로커가 PUBACK(응답)을 줄 때까지 재전송합니다. 유실은 없으나 중복 수신될 수 있습니다.

1. Client ➔ [PUBLISH] ➔ Broker
2. Broker ➔ [PUBACK] ➔ Client

💡 사용처: 도어락 열림/닫힘 상태 알림 (반드시 전달되어야 하지만 중복되어도 상태 덮어쓰기가 가능한 경우)

QoS 2 : Exactly once

정확히 1회 전송 (4-Way 핸드셰이크)

4단계 핸드셰이크를 통해 유실과 중복을 완벽하게 방지합니다. 네트워크 비용이 가장 큽니다.

1. Client ➔ [PUBLISH] ➔ Broker
2. Broker ➔ [PUBREC] ➔ Client
3. Client ➔ [PUBREL] ➔ Broker
4. Broker ➔ [PUBCOMP] ➔ Client

💡 사용처: 스마트 결제 단말기, 의료 기기 원격 투약 명령 (절대 중복되거나 유실되면 안 되는 중요 명령)
