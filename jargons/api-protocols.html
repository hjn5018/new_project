🌐 REST vs GraphQL vs gRPC 실무 시나리오 다이어그램 & 비교

외부 오픈 API(REST), 모바일 종합 대시보드(GraphQL), MSA 내부 초고속 통신(gRPC)의 최적 활용 아키텍처

🎯 1. 3대 프로토콜 실무 적용 시나리오 다이어그램

1. REST API 시나리오 : 공공 오픈 API & 외부 서드파티 결제 연동 범용성 / 캐싱 최우선

전 세계 모든 개발자가 별도 SDK 없이 curl이나 브라우저로 손쉽게 호출할 수 있어야 하는 외부 연동에 가장 적합합니다.

[쇼핑몰 웹/앱] ➔ HTTP POST /api/v1/payments (JSON 바디) ➔ [PortOne / 카카오페이 PG 서버]
[PG 서버] ➔ 카드사 통신 승인 후 ➔ HTTP 200 OK (표준 JSON 응답) 반환
💡 장점: CDN 캐싱 지원, 방화벽 친화적, 전 세계 모든 언어와 호환
2. GraphQL 시나리오 : 모바일 앱 홈 화면 (복합 리소스 단일 호출) 오버패칭 제거 / 단일 엔드포인트

모바일 메인 화면에 1) 사용자 닉네임, 2) 장바구니 개수, 3) 최근 주문 1건이 필요한 경우, REST로는 3번 요청해야 하지만 GraphQL은 단 1번의 쿼리로 필요한 필드만 정확히 가져옵니다.

[모바일 앱] ➔ POST /graphql (query { user { name }, cart { count }, latestOrder { id } }) ➔ [BFF 서버]
[BFF 서버] ➔ 클라이언트가 지정한 필드만 정확히 묶어서 단일 JSON 응답 ➔ [모바일 앱 렌더링]
💡 장점: 모바일 무선망 트래픽 절감, 프론트엔드가 필요한 데이터를 주도적으로 제어
3. gRPC 시나리오 : MSA 백엔드 마이크로서비스 간 초저지연 내부 RPC 통신 초고속 / 초저지연 / 타입 세이프

주문 서버, 재고 서버, 결제 서버 간에 초당 수만 건의 API가 오갈 때, 텍스트 JSON 파싱 비용을 없애고 초소형 Protobuf 바이너리로 통신합니다.

[주문 마이크로서비스] ➔ checkStock(itemId: 101) ➔ [재고 마이크로서비스] (HTTP/2 단 7Byte 바이너리, 2ms)
[주문 마이크로서비스] ➔ processPayment(amount: 50000) ➔ [결제 마이크로서비스] (동일 TCP 파이프 멀티플렉싱)
💡 장점: 직렬화/역직렬화 CPU 낭비 0%, 엄격한 Proto 계약으로 컴파일 타임 에러 검증

📊 2. 3대 API 프로토콜 실제 요청 & 응답 코드 비교

REST API (HTTP/1.1 JSON)

모든 필드가 다 내려오는 Overfetching

// GET /api/v1/users/101
{
  "id": 101,
  "name": "홍길동",
  "email": "hong@test.com",
  "addr": "서울시...",
  "zip": "06012"
}

GraphQL (정밀 쿼리)

원하는 name 필드만 요청 및 수신

query { user(id: 101) { name } }

// [응답]
{ "data": { "user": { "name": "홍길동" } } }

gRPC (Protobuf Binary)

초소형 7바이트 바이너리 프레임

// IDL: user.proto
service UserService {
  rpc GetUser (UserReq) returns (UserReply);
}
// [네트워크 전송: 0A 07 EA B8...]
