💀 DLQ (Dead Letter Queue) 실패 격리 시뮬레이터 & 실무 시나리오 종합

소비(Consume)에 실패한 비동기 메시지를 별도 격리하여 큐 블로킹을 방지하고 수동 재처리(Redrive)하는 파이프라인

🚨 1. 실무에서 DLQ 격리가 발생하는 3대 현실 시나리오

1. 영구 결함 (Poison Pill)

상황: 이미 탈퇴한 회원 ID로 알림톡 발송 요청.
결과: 1,000번 재시도해도 100% 영원히 실패합니다. 이 메시지가 큐 맨 앞을 막으면 뒤의 정상 고객 알림 10만 건이 모두 정지되므로 즉시 DLQ로 빼내어 격리합니다.

2. 외부 시스템 일시 점검

상황: 시중은행/PG사 새벽 정기점검(00:00~00:30)으로 타임아웃 발생.
결과: 메시지가 유실되지 않도록 DLQ에 안전 보관해 둔 뒤, 점검이 끝난 00:35에 관리자가 [Redrive] 버튼을 눌러 일괄 재처리합니다.

3. 페이로드 파싱/스키마 불일치

상황: 클라이언트 구버전 앱 버그로 깨진 JSON 전송.
결과: 역직렬화(Deserialization) 에러로 스프링 리스너가 죽지 않도록 DLQ로 전송하고 개발팀 슬랙으로 에러 페이로드를 통보합니다.

🏦 2. [심층 실무 시나리오] 시중은행 새벽 정기점검(00:00~00:30)과 DLQ Redrive

실제 이커머스/핀테크 서비스에서 매일 자정 발생하는 외부 금융사 점검 시간을 DLQ로 어떻게 완벽히 방어하는지 타임라인으로 확인합니다.

[00:00] 은행 정기점검 시작
시중은행(신한, 국민 등) 코어뱅킹 계정계 시스템이 자정 데이터 배치 정산을 위해 외부 API 연결을 30분간 차단함.
[00:05] 사용자 야간 주문 발생 ➔ 타임아웃 3회 실패
사용자가 5만원 상품을 주문하여 백엔드가 계좌이체/펌뱅킹 API를 호출했으나 SocketTimeoutException 발생.
Spring Retry 지수 백오프(1초 ➔ 2초 ➔ 4초) 3회 시도 모두 실패!
[00:06] DLQ로 안전 격리 (메인 큐 블로킹 차단)
메시지를 영구 삭제하지 않고 bank-transfer-dlq 로 이동시킴.
점검 시간(30분) 동안 발생한 1,200건의 이체 요청 메시지가 DLQ에 차곡차곡 안전 보관됨.
[00:30] 은행 점검 종료 ➔ [00:35] Redrive 원클릭 일괄 재처리
은행 서버 정상화 확인 후, 백엔드 관리자 콘솔에서 [Redrive All] 실행 ➔ DLQ의 1,200건이 메인 큐로 Re-push되어 10초 만에 결제/이체 100% 정상 처리 완료 (유실율 0%)!

📘 4. DLQ 핵심 프로세스 4단계

  1. 1단계 (소비 시도 & 예외): Consumer가 메시지를 수신하여 로직 처리 중 DB 타임아웃/외부 API 장애로 Exception 발생.
  2. 2단계 (지연 재시도 Retry Backoff): 1초, 2초, 4초 등 지수 백오프(Exponential Backoff)를 적용하여 최대 N회(예: 3회) 재시도.
  3. 3단계 (DLX 라우팅 및 격리): 최대 재시도 횟수 초과 시 메인 큐에서 제거 후 Dead Letter Exchange(DLX)를 통해 order-dlq로 자동 격리.
  4. 4단계 (수동 재처리 Redrive & 관제): 장애 복구 후 개발자가 DLQ에 쌓인 메시지의 원인을 분석하고 메인 큐로 Re-push(Redrive)하여 유실 방지.
